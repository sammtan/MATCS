CHAPTER 1
INTRODUCTION

1.1 Background

Traffic congestion is a common problem in urban areas. The number of vehicles using a road
can change according to the time of day, commuting patterns, weather, public activities,
incidents, and other conditions. Because traffic demand changes over time, a
traffic-management system that uses only a fixed pattern may not always use available road

capacity effectively.

Traffic lights are important for organizing vehicle movement through road intersections. They
assign the right of way to different approaches and help prevent conflicting movements.
However, if every approach receives the same timing even when its traffic demand is
different, one approach may develop a long queue while another approach has unused

green-light time. This can increase waiting time, vehicle stops, and overall delay.

The problem becomes more difficult when several intersections are connected by the same
toad corridor. Vehicles released from one intersection may travel toward another intersection
and create a queue there. Therefore, a decision that reduces congestion at one intersection
may transfer congestion to a neighboring intersection if the wider traffic condition is not
considered. A traffic-control approach for connected intersections should consider local
conditions and, when the system is expanded, relevant information from neighboring

intersections.

Artificial intelligence can support traffic-management research by helping a system analyze
changing traffic conditions and select actions according to a defined objective. Agentic AI is
televant to this problem because the system can be organized into software components with
specific responsibilities. For example, one component can process observations, another can
maintain the current state, and a controller can propose a signal action. In a multi-intersection
expansion, local controller agents may coordinate through summarized information from

connected intersections.

--- PAGE Team Report (current_ Chapter 3 (Project Design))_page-0003.jpg ---

Based on this problem, Group 14 proposes the Multi-Agent Traffic Control System
(MATCS). MATCS is a software-only, simulation-first project that models traffic demand,
vehicle movement, traffic-light phases, and controller decisions in a defined area. The system
teceives or synthesizes traffic observations, creates a representation of the current simulation
state, proposes a traffic-light action, validates that action using deterministic safety rules, and

applies the validated action to the simulator.

The first implementation target is one simulated area containing one intersection. This scope
is intentionally limited so that the team can demonstrate the complete feedback loop before
introducing the additional complexity of multiple connected intersections. The first controller
is a fixed-time baseline. Later work may compare it with a queue-aware controller and, if the

tesults and project schedule justify it, an optimization or leamed controller.

MATCS does not connect to or control public traffic-light hardware. The system imitates the
interfaces and feedback flow of a possible real-world system while keeping actuation inside
the simulator. This boundary is necessary because public traffic control is safety-critical,

legally controlled, and outside the scope of this student project.

The main objective of the project is to investigate whether a data-driven traffic-light
controller can improve traffic-flow measures such as travel time, delay, queue length,
throughput, and the number of stops in repeatable simulation scenarios. Reducing estimated
emissions or fuel consumption may be considered a secondary objective when the selected
simulator provides a credible measurement proxy. Any improvement must still respect

signal-safety constraints and must not unfairly starve one approach.

The project supports a live public-facing demonstration of the simulation near the end of the
course. The demonstration shows simulated traffic and controller behavior, not real-world
traffic-light control. This report presents the project background, requirements,

project-management process, risk management, and initial technical direction.

1.2 Problem Statement

Urban traffic demand changes over time, but fixed traffic-light schedules may not respond to
those changes. This can create unnecessary delay and queues. Connected intersections
introduce an additional coordination problem because releasing traffic from one intersection

can affect downstream conditions.

MATCS addresses this problem as a simulation and software-engineering study: how can a
traffic-control system represent changing traffic conditions, propose safe signal actions, and

evaluate local and coordinated control strategies using reproducible experiments?

1.3 Project Objectives
1.3.1 Primary Objective

The primary objective is to design and evaluate a simulation-based traffic-control system that
aims to improve traffic flow by reducing delay, travel time, queue length, and unnecessary

stops while maintaining safe signal transitions.
1.3.2 Secondary Objective

The secondary objective is to investigate whether improved traffic flow can also reduce an
emissions or fuel-consumption proxy when the selected simulator supports such a

measurement.
1.3.3 Engineering Objectives
The engineering objectives are:

e Define a reproducible one-intersection simulation scenario.

e Implement or configure a fixed-time controller baseline.

e Define observation, state, proposal, validation, actuation, and metric contracts.

e Compare later controllers against the fixed-time baseline using matched scenarios.

e Keep the system simulation-only and suitable for a live public demonstration.

e Manage the project using a traceable and lightweight process appropriate for a

three-student team.

are preferred.

The Class Diagram describes the main classes and their relationships in MATCS. The central

Figure 3.5. State Diagram of MATCS

The State Diagram depicts the possible states of a traffic light approach within the MATCS
environment and the conditions that trigger transitions between these states. A traffic light
typically cycles through the Red, Green, and Yellow phases. A transition from the Red phase
to the Green phase occurs when the controller allocates the right of way to a specific
approach and the proposal successfully passes the SafetyValidator. The Green state transitions
to the Yellow state either when its maximum allocated duration expires or when the controller
decides to switch phases due to changing traffic conditions. The Yellow state is a transient
state that automatically transitions back to Red after a fixed yellow time duration.
Additionally, if any proposed action fails the safety validation at any point, the system

transitions to a Safe Fallback state to prevent conflicting movements.

Figure 3.6. Helicopter View of the Design - MATCS

The Helicopter View of MATCS provides a high-level overview of how the main components
of the system are connected during the traffic simulation process. The system involves two
types of users: Traffic Officers, who can view the intersection state, traffic metrics, and
controller decision logs, and Researchers/Operators, who can configure scenarios, select

controllers, run simulations, compare results, and replay recorded runs.

User inputs are provided through the Web Dashboard (User Interface), which is used to

configure simulation parameters such as the scenario, controller, duration, and random seed.

--- PAGE Team Report (current_ Chapter 3 (Project Design))_page-0022.jpg ---

The dashboard also allows users to start or stop the simulation, view the current intersection

state, and display traffic metrics and logs.

The main processing is handled by the MATCS Core (Backend), which consists of the
Simulator Adapter, State Builder, Signal Controller, Safety Validator, and Action Applier.
The Simulator Adapter receives traffic observations from the simulator, while the State
Builder uses these observations to build the intersection state. The Signal Controller then
generates a signal proposal, which is checked by the Safety Validator before being applied to
the simulator. If the proposed action does not satisfy the safety rules, a safe fallback can be

applied instead.

The Traffic Simulator, such as SUMO, is responsible for simulating traffic flow, providing
traffic observations such as vehicle counts and queue lengths, and receiving signal actions
from MATCS. During the simulation, the Metrics Collector & Logger calculates performance
metrics, stores simulation states, actions, and logs, and provides the processed data for
visualization. The simulation results are stored in the Database/Run Repository, while the
Metrics & Visualization Module processes the metrics and provides data for dashboard

visualization and controller comparison.

Overall, the Helicopter View illustrates the main system flow of MATCS, starting from user
input and dashboard configuration, continuing through traffic observation, state building,
signal proposal, safety validation, and action application, and ending with data collection,

storage, and visualization.
